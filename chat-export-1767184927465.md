## Core idea
 
### 1) One universal **Timer Engine**
 
A timer is just a set of **players**, **clocks**, and **events**.
 
**Events** (things that happen):
 
- Tap player A
- Tap player B
- Pause / resume
- Undo
- Time expires
- Capture occurs (optional for games like Go variants)
- Round ends / new round starts
 
**Actions** (what the engine does when events happen):
 
- Switch active player
- Add increment / delay
- Reset a player’s clock to a fixed value
- Subtract a “move token”
- Start/stop a phase timer
- Trigger sound / haptics / alert
- Apply penalties (e.g., -5 seconds)
 
This lets you build chess timers *and* your “tap resets to N seconds” timer as presets.
 
---
 
## Game formats as “Presets”
 
A **Preset** is a JSON-like config (stored locally) describing:
 
- Number of players/teams
- One or more phases (optional)
- Per-player timers and rules
- Tap behavior
- Win/lose conditions
- Optional counters (captures, rounds, points)
 
### Example Preset Types
 
**A) Blitz Chess**
 
- 2 players
- Main clock: 5:00 each
- Tap ends your turn → switches active player
- Increment: +0:03 after tap (Fischer)
- Loss condition: your clock hits 0
 
**B) Classical Chess with Delay**
 
- 2 players
- Main clock: 60:00
- Delay: 0:10 per move (Bronstein/US delay style)
- Tap ends your turn → switches active player
 
**C) “N-second per move” reset timer (what you described)**
 
- 2+ players
- Each player has a move clock of N seconds (e.g., 30)
- When you tap “end turn”:
 
- your move clock **resets back to N**
- active player switches
- Optional: if you run out (hit 0) you “lose the round” or take a penalty point, but the match continues
 
That last one is super common in casual games, trivia, speed Go variants, etc.—and most timer apps don’t model it well.
 
---
 
## Rules layer (to support “thousands of games”)
 
Instead of building 5,000 bespoke modes, you support **building blocks**:
 
### Building blocks
 
**Timer behaviors**
 
- Count down (normal)
- Count up (stopwatch)
- Move timer (resets each turn)
- Byo-yomi / overtime periods (Go/board variants)
- Sand-clock pool shared by team (hot potato style)
 
**Turn logic**
 
- Alternating turns (A↔B)
- Turn order list (A→B→C→D)
- Team turns (Team 1 player order, then Team 2 player order)
- “Pass” option (doesn’t switch, or switches differently)
 
**Add-ons**
 
- Counters: captures, rounds won, points, penalties
- Phases: setup phase, main phase, overtime phase
- Triggers: “after 10 moves”, “after 5 minutes”, “if capture count reaches X”
 
This gets you “supports thousands of games” because users are basically assembling a preset from LEGO pieces.

## Key Flutter detail: don’t let timers drift
 
Common timer bug: relying on `Timer.periodic` timing exactly every 1s.
 
Better:
 
- UI/App layer tracks real time with `Stopwatch`
- Every frame or 50ms:
 
- compute `elapsed = stopwatch.elapsed - lastElapsed`
- dispatch a `Tick(elapsed)` event
- Engine updates remaining time based on `elapsed`
 
This makes it accurate even if the phone lags.

## Core idea
 
### 1) One universal **Timer Engine**
 
A timer is just a set of **players**, **clocks**, and **events**.
 
**Events** (things that happen):
 
- Tap player A
- Tap player B
- Pause / resume
- Undo
- Time expires
- Capture occurs (optional for games like Go variants)
- Round ends / new round starts
 
**Actions** (what the engine does when events happen):
 
- Switch active player
- Add increment / delay
- Reset a player’s clock to a fixed value
- Subtract a “move token”
- Start/stop a phase timer
- Trigger sound / haptics / alert
- Apply penalties (e.g., -5 seconds)
 
This lets you build chess timers *and* your “tap resets to N seconds” timer as presets.
 
---
 
## Game formats as “Presets”
 
A **Preset** is a JSON-like config (stored locally) describing:
 
- Number of players/teams
- One or more phases (optional)
- Per-player timers and rules
- Tap behavior
- Win/lose conditions
- Optional counters (captures, rounds, points)
 
### Example Preset Types
 
**A) Blitz Chess**
 
- 2 players
- Main clock: 5:00 each
- Tap ends your turn → switches active player
- Increment: +0:03 after tap (Fischer)
- Loss condition: your clock hits 0
 
**B) Classical Chess with Delay**
 
- 2 players
- Main clock: 60:00
- Delay: 0:10 per move (Bronstein/US delay style)
- Tap ends your turn → switches active player
 
**C) “N-second per move” reset timer (what you described)**
 
- 2+ players
- Each player has a move clock of N seconds (e.g., 30)
- When you tap “end turn”:
 
- your move clock **resets back to N**
- active player switches
- Optional: if you run out (hit 0) you “lose the round” or take a penalty point, but the match continues
 
That last one is super common in casual games, trivia, speed Go variants, etc.—and most timer apps don’t model it well.

## Rules layer (to support “thousands of games”)
 
Instead of building 5,000 bespoke modes, you support **building blocks**:
 
### Building blocks
 
**Timer behaviors**
 
- Count down (normal)
- Count up (stopwatch)
- Move timer (resets each turn)
- Byo-yomi / overtime periods (Go/board variants)
- Sand-clock pool shared by team (hot potato style)
 
**Turn logic**
 
- Alternating turns (A↔B)
- Turn order list (A→B→C→D)
- Team turns (Team 1 player order, then Team 2 player order)
- “Pass” option (doesn’t switch, or switches differently)
 
**Add-ons**
 
- Counters: captures, rounds won, points, penalties
- Phases: setup phase, main phase, overtime phase
- Triggers: “after 10 moves”, “after 5 minutes”, “if capture count reaches X”
 
This gets you “supports thousands of games” because users are basically assembling a preset from LEGO pieces.

## Key Flutter detail: don’t let timers drift
 
Common timer bug: relying on `Timer.periodic` timing exactly every 1s.
 
Better:
 
- UI/App layer tracks real time with `Stopwatch`
- Every frame or 50ms:
 
- compute `elapsed = stopwatch.elapsed - lastElapsed`
- dispatch a `Tick(elapsed)` event
- Engine updates remaining time based on `elapsed`
 
This makes it accurate even if the phone lags.
